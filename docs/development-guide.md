# 開発ガイド（伴走・学習優先）

最終更新: 2026-08-23

Enerifc は「動くもの」と同時に、実装者（あなた）が **自分の言葉で説明できること** を目標にする。エージェントは代行メーカーではなく、隣で設計を言語化する伴走者として動く。

## 1. 作業の前に

毎回、関係する docs を読む。最低限:

- [requirements.md](./requirements.md) … その機能が MVP か
- [progress.md](./progress.md) … 今のスライスか、1000 行に収まるか
- 変更対象の設計文書（database / architecture / sitemap 等）

コードと docs が食い違うときは **先に docs を直す提案** をする。黙って仕様変更しない。

## 2. 伴走のやり方

エージェントがやること:

- スライスの目的を 3〜5 行で書く
- 触るファイルと、意図的に触らない範囲を先に示す
- Prisma / SQL / API の「なぜこの形か」を日本語で残す（長文コメントより docs とコミットメッセージ）
- 生成したら、レビュー用に「自分で確認してほしい点」を箇条書きする

あなたにやってもらいたいこと:

- 差分を読み、不明な行を質問する（理解できないままマージしない）
- 小さな課題は自分で書く（例: enum を 1 つ足す、seed の 1 テーブル、テスト 1 本）
- 外部講師レビューの単位を意識して「ここまでで切る」と判断する

エージェントがやらないこと:

- 説明なしの巨大スキャフォールド
- フロントとバックエンドの同時盛り
- 「ついで」のリファクタでレビュー枠を埋める

## 3. 実装順序

**バックエンドが先。** 画面は、そのスライスの API またはスキーマがレビュー可能な形になってから。

例外: That Open の **表示だけ** のスパイク（サンプル IFC を 1 画面に出す）は、抽出ロジックより前にやってもよい。DB と繋がないこと。スパイクも 1000 行ルール対象。

## 4. レビュー 1000 行ルール

外部講師への 1 回の依頼は、追加・削除を合わせて **おおむね 1000 行まで**。

数え方の目安:

- `git diff --stat` の挿入＋削除
- `package-lock.json` はレビュー対象から外してよい（講師にその旨を伝える）
- Prisma の生成物 `node_modules/.prisma` はコミットしない
- 大きな seed JSON は「データ PR」と「ロジック PR」に分ける

切り方の例は [progress.md](./progress.md)。1 スライスが膨らみそうなら、実装前に分割案を出す。

実装をフェーズ末まで進めてから講師に依頼してよい。Phase B は B1〜B7 を 1 依頼にまとめる（[decisions.md](./decisions.md) DEC-16）。他フェーズは原則 1000 行。

## 5. ブランチとコミット

- 機能ブランチ: `feat/phase-b-prisma-init` のようにフェーズ＋内容
- コミットは「なぜ」が分かる一文。ユーザーからコミット指示があるまでエージェントはコミットしない
- 秘密情報（`.env`, サービスロールキー）をコミットしない

## 6. コードの好み（小さく保つ）

- 1 ファイルにユースケースを詰め込まない。Route Handler は入出力、ロジックは `lib/`
- `any` を増やさない。外部 API の JSON は型を狭くパースする
- 日本語 UI 文言は定数または小さな辞書。コンポーネントにベタ書きしすぎない（フロント開始時）
- That Open はブラウザ専用モジュールに隔離し、サーバコードから import しない

## 7. 確認の仕方

バックエンド期間:

- Prisma migrate が空の Supabase に通る
- seed 後にマスタ件数が [master-data.md](./master-data.md) と一致する
- 認証なしで他人の案件 API が 401/403
- 自分の案件だけ読める

フロント開始後: ブラウザでモック経路を辿る（ユーザー規則どおり）。そのときも docs の URL を正とする。
